## [Unreleased]

### Added
- Global model table (`-model-table`, server scope, repeatable): the gateway's client-visible model identities are declared once as `surrogate@provider=wire[;facts]`. Surrogates are a single global namespace (a duplicate is a startup error) and each transcoded mount serves exactly the entries naming it: the table is projected onto that mount's model map at startup, identity fallback is off, and a request naming an unlisted model is a local 400 that names the mount's servable surrogates. The wire id is opaque to the shaper and never appears in a client response; optional facts (`context`, `max_output`, `efforts`, `modalities`, `default`, `deprecated`, `cost_input`, `cost_output`, `tags`, `description`, `created`) are validated at startup, are presentation-only, and are echoed by the startup summary line. With no entries the previous behavior is unchanged, entry for entry; an entry naming a passthrough-only provider is rejected because that mount cannot resolve the advertised surrogate to its wire id.
- Gateway-hosted model catalog (`GET /v1/models` per mount): when `-model-table` names a mount, discovery is answered locally from the frozen table, never contacting the upstream and never queueing behind in-flight completions, even under `-limit-all` or an open circuit breaker. The served dialect is selected by `?format=` (aliases `responses`/`messages` accepted), the Codex `?client_version=` probe (native `{"models":[...]}`), an `Anthropic-Version`/`Anthropic-Beta` header (messages list with `after_id`/`before_id`/`limit` pagination and capability objects), or the mount's default (Responses to Codex, Messages to Anthropic, otherwise the lean OpenAI list). Wire ids never appear in a served document; optional facts are omitted or `null`; Anthropic capability claims stay null until the table can describe the complete matrix; Codex-required fields use conservative false/32K-token fallbacks; repeated or malformed query values are rejected; one malformed entry is skipped rather than failing the listing; unknown query parameters and formats are bounded local 400s that are never forwarded. A mount with no entries keeps the route a transparent passthrough.
- Multipart `tool_result` images (`-transcode-chat-capability tool_result_images`, off by default): with the capability granted, multimodal tool-result content (text, image, and document parts, as emitted by Claude Code agentic replay) renders as MULTIPART content blocks inside a chat tool message with order preserved, for upstreams that accept image parts there — without it a vision model is blind to the image. The pinned Chat contract does model message content as either a string or an array of blocks for any role, but real gateways differ on whether they accept image parts inside `role: "tool"`, so the opt-in is the honest default. Granting the capability is independent of `image_input`, though the multipart form itself needs the `image_url` vocabulary, so a mount that withdraws `image_input` renders the envelope either way. A result part the multipart form cannot carry (a document block) or an image media type the encoder rejects falls back to the deterministic `tool_result_json_envelope` text, recorded, never dropped. The wire shadow's modeled-extension comments record the observed behaviour.
- Chat image-detail mapping: the Chat Completions dialect defines only `auto`, `low`, and `high` for an image's detail, so the two other cases are decided explicitly and observably. The Responses-only value `original` is a client-requested fidelity knob, so mapping it to `high` - the closest truthful semantic, since `original` means the full-fidelity request - is a policy-gated `image_detail_original` loss rather than a silent downgrade: it is approved by default, and an operator can refuse it with `-transcode-loss-strict` or a negated key, exactly as for every other fidelity-only knob. A source dialect with no detail field at all (an Anthropic Messages image block) is different: that is proxy-invented content rather than a client request, so the documented `auto` default is recorded as an ungated `image_detail_invented` note and takes no policy decision. Any other unexpected value is rejected rather than passed through, and an empty value is treated as the source having no field rather than as an explicit choice. Before this, a Responses request carrying `detail: "original"` forwarded that value verbatim onto a Chat upstream, where it is not part of the dialect.
- Anthropic server-side tools (`-transcode-allow-loss anthropic_server_tools`, strict by default): Claude Code's type-discriminated tool definitions (`web_search_20250305`, `code_execution_20250825`, and the other modelled spellings) and its server-executed or server-referencing content blocks are admitted on the wire with their raw bytes preserved, then dropped observably rather than forwarded - a chat upstream executes no server tools. A `server_tool_use` is never fabricated into a tool call, because a call with no executor would dangle and corrupt tool pairing. The key is a policy-gated loss and is NOT in the default approved set, so a Claude Code web-search session against a chat upstream fails with a named error until the operator approves it; previously it failed with an unattributed unknown-field error. A `tools[]` entry is classified by its `type` discriminant: the client-function spellings (absent, or the explicit `"type":"function"`) decode strictly and are carried through, and ANY other type takes the same policy-gated loss - so a new Anthropic server tool becomes usable by approving the flag, with no proxy rebuild, and is never silently dropped or hard-rejected by an error the flag cannot clear. A real `mcp_tool_use` carries `server_name`, which is decoded. `mcp_tool_use` and `mcp_tool_result` are client-side tools that map 1:1 onto `tool_use` and `tool_result` and carry no loss. The shapes are modeled beyond the pinned Anthropic Messages revision; The wire shadow's modeled-extension comments record them and the capture they came from.
- Camel `format` marker on a Responses reasoning item (modeled extension beyond the pin, documented in the wire shadow with a captured `camel_reasoning_format_field.json`): the Responses output-item union is strict, so an unmodelled key would reject the whole response. The value is therefore decoded off the wire, then cleared before the canonical `Raw` bytes are taken on decode, so the marker never reaches a client and never changes the canonical bytes. That single decode-side cut is the only one needed: the render site never sees a decoded marker, and a defensive clear there was verified dead and removed. The stream path deliberately retains it in the decoded item.
- Data-only SSE frames (ungated `missing_event_name` note): the SSE `event:` field is optional, and the JSON `type` is the authoritative discriminator. A frame that omits the name is now routed by its decoded type rather than rejected, and the provider quirk is recorded once per stream. A PRESENT name that disagrees with the JSON type is still a wire error, and the strict event union runs first, so an unknown or misspelled `type` still rejects. Backed by a captured `data_only_responses_stream_field.sse`.
- Multi-agent protocol priming (`-transcode-chat-capability multi_agent_priming`, off by default, chat upstreams only): for models not trained on the harness orchestration protocol, a bounded reminder naming the `spawn_agent` / `wait_agent` / `send_input` / `close_agent` / `resume_agent` discipline is appended **after** the client's own leading system (or developer) instructions, so the client's bytes and their order are unchanged and the reminder is strictly last. The reminder is injected only when the request actually declares one of the tools it names - checked against the FLAT names the upstream will see, so a flattened namespace child still counts - so the text never names a tool the upstream was not sent. When the request has no leading system turn, a system turn carrying only the reminder is prepended, and when the leading turn is a developer turn the reminder is appended in place. Every injection path records a note (`multi_agent_priming`); the text is a compile-time constant whose claims were checked against the captured `multi_agent_v1` schema, not written from memory. The note is registered as Note-only and is deliberately absent from the loss registry, so it is never a policy-gated loss and appears in no `-transcode-allow-loss` list. Accepted and ignored on a Responses upstream, as are the other chat-only capabilities.
- Agent profile routing (`-transcode-profile name=model[:tier]`, provider scope, repeatable): an abstract profile name maps to a concrete upstream model and an optional reasoning tier, so agents that select a model by role name are served the model an operator assigned to that role. The profile name is a client-side identity only — the upstream request carries the resolved wire model, and the client response echoes the profile name rather than the wire id, so the wire model never leaks through a transcoded exchange. A profile's tier applies only when the client specified neither reasoning effort nor a thinking block — an explicit client choice always wins — and, on a Chat Completions upstream, only when that mount has the `reasoning_effort` capability; without it the tier is inert rather than a client-visible drop, since no client-requested feature was lost. Startup validates every profile target against the mount's resolved model map or projected model table, and a target that cannot be resolved is a startup error naming the profile and the model, never a per-request surprise. A profile name that is also a mapped model is rejected at startup rather than silently shadowing that mapping, because the client would otherwise be told the mapped name while being served the profile's target. With no profiles configured, model resolution is unchanged.
- Responses namespace tools (the Codex CLI's `multi_agent_v1` subagent group, MCP server groups, and any other `type:"namespace"` grouping) are flattened into ordinary chat function tools on the request path, and a model call to a flattened child returns the bare child name plus its separate `namespace` field — never a concatenated name — for both streaming and non-streaming exchanges. A child that collides with a plain tool or another namespace's child is qualified deterministically (`namespace__child`) and mapped back from the per-exchange flattening map (name separators are never parsed); replayed `function_call`/`function_call_output` history keeps the same flat names so an upstream is never taught the bare form. The `type:"namespace"` tool and the call items' optional `namespace` field are modeled beyond the pinned OpenAI SDK revision (documented in the wire shadow's modeled-extension comments), and each flattened namespace is named in the per-request loss/note line.
- Conversation continuity store (`-transcode-continuity`, provider scope, off by default): when enabled, the shaper retains the canonical conversation behind each emitted Responses id, so a follow-up request carrying `previous_response_id` is reconstructed against a stateless chat upstream instead of being forwarded with an id the upstream cannot resolve. A hit is observable (the existing `previous_response_id` loss is skipped, since the field was genuinely consumed) and a miss — unknown, expired, or an id from another provider — degrades to that same pre-existing observable loss, never a failure. The store is bounded by `-transcode-continuity-capacity` (default 1024, evicting the oldest chain) and `-transcode-continuity-ttl` (default 30m); both reject negative values at startup, and each eviction is logged with the operator's other local conversion errors. Retained ids are scoped per provider, so a chain cannot be resolved by another mount. The client-visible `store:false` is honoured: such a response retains nothing. Streaming and non-streaming exchanges retain the same turns, and every other protocol direction is a no-op. With the flag unset nothing is retained and `previous_response_id` keeps its existing loss exactly.
- Full-flow diagnostic recorder (`-transcode-flowlog-dir`, provider scope, off by default): each transcoded exchange writes one JSON file into the existing directory capturing the complete flow — client request, converted upstream request, upstream response, downstream response (all with headers and full bodies), the request/response conversion reports, the recorded outcome, and the exchange duration — for debugging a live exchange whose aggregated `transcode:` log lines are not enough. Bodies are verbatim (base64 when not valid UTF-8), each streamed body is capped at 64 MiB with a truncation flag, the filename carries the pid so concurrent processes cannot overwrite each other, and startup fails with a clear error when the directory does not exist. Nothing is redacted, so the directory must be treated as secret-bearing; the recorder is fully inert when the flag is empty.
- Fleet header wrap-all reflow: in multi-provider `-tui` mode the header never leaves a truncated first provider chip alone on row 0 — chips share row 0 only when the first fits at its natural width beside the fleet identity body, otherwise row 0 stays body-only and every chip starts on the next row at full width, with clicks tracking the rendered spans (`chipRowsLayout` is the single source of truth for rendering and hit-testing). Breakpoints are dynamic (natural-fit, not fixed thresholds): narrow terminals show body-only row 0 with legible wrapped chips, wide terminals share leading chips beside the body, and short terminals cap rows so content keeps a row. The active tab and active provider chip share one fill per theme (dark `#58A6FF`, light `#0550AE`) distinct from the header bar, both clearing WCAG AA with margin, and the hot path carries allocation ceilings, grapheme-width pins (CJK/emoji/combining), and height-cap edge coverage.
- SSE queue comments (`-queue-comments`, opt-in): for streaming requests (the `Accept` header selects `text/event-stream`), the proxy commits `200` + SSE headers before admission and emits `: queue-wait elapsed=N` comment lines while the request waits for a slot — the connection stays visibly alive instead of silently blocking, and agents that watch for stream activity see progress. The exchange is locked to the streaming representation once committed: later failures surface as failed streams — a `queue-wait failed` comment followed by a closed stream (every SSE client treats a stream ending without its terminal event as an error, never a success) — never as a new HTTP status inside the committed stream. The proxy is dialect-agnostic on transparent routes, so no provider-specific error event is synthesized. Comments flow through BOTH the per-route and the global limiter waits and stop before the real response streams. Body-carrying requests require a full-duplex-capable downstream connection (standard for net/http servers); a writer that cannot enable full duplex falls back to the silent-queuing semantics — the early commit never corrupts an unread request body. Default `0` = disabled (blocking semantics unchanged).
- Per-route queue observability (`QueuedByRoute` / `OldestQueuedAgeByRoute` in the metrics snapshot; per-route breakdown in the TUI Queue Depth panel): the aggregate queued count hid WHICH route was starved — the breakdown shows each waiting route and how long its oldest waiter has waited. Also fixes the queued-state detection it is built on: an in-flight request now registers with a zero start time (the queued convention the in-flight sort and oldest-queued-age logic already assumed), so `OldestQueuedAge` — permanently zero since inception — actually reports. The Prometheus endpoint exports the aggregate `shaper_oldest_queued_seconds` gauge (the oldest LIMITED request waiting on either limiter, per-route or global; passthrough requests blocked in the global limiter count toward `shaper_queued` but carry no queue age) and, while requests are waiting in per-route queues, the `shaper_route_queued` and `shaper_route_oldest_queued_seconds` families with `method` and `path` labels (one contiguous block per family across all providers; routes with no waiters export no series, and a route whose `method` or `path` label value is not valid UTF-8 exports no series at all — the text parser rejects the whole document on an invalid label value, so the series is skipped, never sanitized).
- Native thinking rendering (`provider_reasoning_thinking` capability): provider plaintext reasoning (the chat `reasoning`/`reasoning_content` extension) maps to NATIVE Anthropic thinking blocks, so Claude Code renders it with its native thinking UI instead of ordinary text. Each synthesized block carries the proxy's marker signature (`shaper-synth-thinking-1`), and the Messages request path scrubs marker-signature thinking blocks out of replayed history before any upstream rendering — the synthetic signature never reaches an upstream, so the documented signature-rejection failures cannot occur. Streaming emits the exact Anthropic thinking lifecycle (content_block_start with an empty signature → thinking_delta → signature_delta → content_block_stop, preceding the text block); non-streaming renders a thinking content block. `redacted_thinking` is never synthesized. Without the capability, behavior is unchanged (ordinary-text mapping under `provider_reasoning_text`).
- Bounded-queue admission (`-queue-depth`): cap how many limited requests may wait for a slot at once. When the bound is reached, arriving requests fail fast with `429 Too Many Requests` + `Retry-After` and a JSON error body valid under both AI dialects' envelope conventions — the signal the official SDKs and agents like Claude Code already act on (retry with a visible countdown) — instead of queueing silently until the client's own deadline aborts and retries the request. The default (`0`) preserves the documented blocking-until-admit semantics exactly. The new `shaper_queue_rejected_total` metric counts the rejections. (The opt-in stream-only queue-comment mode from the prior-art research is deferred: emitting SSE comments before admission requires committing `200` and restructuring header commitment on every downstream path; recorded as deferred.)
- The unlimited admission class: a `-limit` pattern with an `:unlimited` suffix (`POST /messages/count_tokens:unlimited`) exempts matching requests from concurrency limiting entirely — including under `-limit-all` — so cheap auxiliary calls (token counting, health checks) can never queue behind long-running streaming completions. The class carries no limiter and cannot declare a `@group`; the first matching pattern decides (the same rule limiter selection uses), and unlimited requests count as passthrough in metrics and the TUI. This is the structural fix for the reported unresponsive-agent failure mode where a `count_tokens` probe queued behind 80–200s completions under `-limit-all`.


- Native model passthrough (`-native-route protocol@path`, provider scope, repeatable; `-model-table` gains the routing-active `via` fact): an upstream that serves different models on different dialects — Responses on `/v1/responses`, Messages on `/v1/messages`, Chat on `/v1/chat/completions` — is no longer forced through one conversion. A request whose model's `via` dialect matches a declared native route is forwarded through the existing engine with **only the model identifier rewritten** and every other byte preserved (the value is spliced in place, not re-marshaled); a non-streaming response gets the client-facing name restored inside the response bound, while a streaming response passes through byte-identically. Validation on this path is **structural only** — duplicate JSON keys at any depth, trailing values, malformed syntax, and a usable `model` field are rejected, while field coverage and union validity belong to the upstream that owns the dialect (its own error is authoritative), so documented optional controls and a tool without an explicit `strict` are forwarded rather than rejected. A native route may **share its client path with a transcode mapping**: dispatch serves a dialect match natively and falls through to the mapping on a mismatch, so one path serves some models natively and converts the rest; a known model with no route or mapping for its dialect fails closed with a dialect-shaped 404 naming its native dialect, and an identity-resolved model keeps legacy transparent behavior. `-native-route` without any `via` entry logs a startup note rather than sitting silently inert.
- opencode first-party request shape (`-opencode`, provider scope, off by default; `-opencode-user-agent`, `-opencode-client` overrides): OpenCode gateway routes requests to different backend providers per conversation and requires a stable session value to pin them, so a client that does not send one fails upstream. Enabling the preset reproduces the first-party shape on every outbound path — transparent, native, and transcoded — emitting `User-Agent`, `x-opencode-client`, the session value, and the client's own identity/project/parent headers only when it sent them (never fabricated). The impersonation markers are preset-authoritative — the upstream sees the first-party `User-Agent` and client attribution rather than a client's own, so a claude-code or SDK client cannot identify itself through them — while the session stays the client's own value when it sent one. A different client SDK's fingerprint headers (`x-stainless-*`, `x-app`) are removed, since a real opencode client sends none and they would reveal the actual client. The preset leaves the dialect's protocol headers alone; note separately that on a mount with an upstream credential configured, credential stripping removes `anthropic-version` and `anthropic-beta` before the preset runs, on the transparent path as well as the native one, while a transcoded mapping restores `anthropic-version` from its auth policy and a native route does not. The session value prefers the client's `x-opencode-session`, then `x-session-affinity`, then `X-Session-Id`, and otherwise derives a stable opaque key from the conversation's own provider, client model, and first user turn (or the client address where the body is not buffered), so repeated turns of one conversation reuse one value across native and converted serving alike. Headers are applied **after** authentication, so the mock never clobbers a credential, and header values are never logged. A mount whose upstream host is not `opencode.ai` logs a startup note instead of impersonating silently, and mounts without the flag forward byte-identically. The observed upstream contract is recorded in `docs/opencode-zen-contract.md`.
- Catalog suites answer the Claude Code token probe and route chat completions: `POST /v1/chat/completions` is now a suite completion route (a chat-native model is routed to its provider), and `POST /v1/messages/count_tokens` is answered in the Anthropic dialect instead of a bare 404 page, so a Claude Code gateway probe gets a shaped response either way. `GET /v1/models?limit=1000` discovery and `?beta=true` inference already worked through the suite; a chat error is rendered in the OpenAI envelope even when the suite's catalog defaults to the Anthropic shape.

### Fixed
- `-auth-mode header:<name>` no longer accepts a header name the proxy pipeline manages, on any mount. A mount that resolved to one started cleanly and then lost the credential silently, because the name was stripped, overwritten, or removed after authentication had attached it — the client saw a bare 401 with nothing in the log. Reserved names are now refused at startup: the always-managed ones (`authorization`, `content-type`, the `x-amz-*`/`x-goog-*` prefixes, hop-by-hop and conditional headers) always, and the opencode preset's own set (`user-agent`, `x-opencode-client`, the session trio, the request/project/parent headers, `x-app`, `x-stainless-*`) while `-opencode` is enabled. The preset rule is scoped: those names remain legal credential targets with `-opencode` off, and a custom name such as `header:X-Api-Token` is accepted with the preset on. The preset-managed set is derived from the preset's own disposition table, so a new preset header or SDK fingerprint cannot reopen the hole. Pinned by config and mapping cases in both directions, and end-to-end against the real binary, which is the only layer that applies authentication and the preset in the order that broke.
- An upstream chat stream that omits the `[DONE]` sentinel after a finishing chunk no longer fails a completed exchange: the held terminal is released on upstream EOF (the documented contract) and the provider quirk is recorded as the ungated `missing_stream_sentinel` note, so the completion is reported truthfully instead of as a truncated stream. A stream that ends before any `finish_reason` still fails as a typed truncation with a client-dialect error event — the release never fabricates a success. Observed live through `-transcode-messages-chat`: a gateway that sometimes closes the connection right after the final chunk (with the usage tail) instead of sending the sentinel failed streaming exchanges as `chat stream ended after finish_reason without the [DONE] sentinel`. One real Claude Code exchange failed before any content frame arrived and another failed after thinking deltas only, so the completing text block was never delivered in the failed exchange; a sibling exchange on the same gateway sent the sentinel and completed. Every affected exchange was client-visibly errored and counted as an upstream failure, and the release is pinned by a regression test that replays the captured no-sentinel stream verbatim.
- Native Responses upstreams that echo explicit nulls in their envelope no longer fail the strict decode: `prompt_cache_key`, `safety_identifier` (and the analogous nullable echo fields) accept an explicit `null` as absent on the response path. Observed live: a gateway serving the native Responses API put explicit nulls in every response, failing every exchange of `-transcode-messages-responses` in local response conversion.
- Two benign upstream chat-stream shapes no longer fail an exchange: a legacy `function_call` fragment whose `name` and `arguments` are both present and empty is a no-op equivalent to null (it carries no invocation), and the optional usage-only tail chunk may omit its envelope identity (`id`/`model`/`created`) — a content-bearing chunk missing any of them still rejects, and `{}`, a fragment whose `name` is present and empty, and member-level nulls still reject (a bare `function_call: null` is treated as absent, matching the wire). Observed on verboo `glm-5.3-flash` through `-transcode-messages-chat`.
- Multimodal `tool_result` content (image/document/mixed, as emitted by Claude Code agentic replay) no longer fails a Messages→Chat conversion with a 400: `tool_result_multimodal_content` and `tool_result_json_envelope` joined the default approved losses, so the content is encoded observably as the deterministic `transcode_version 1` JSON text envelope inside the Chat tool message, with the correction logged per exchange (the strict policy and `-transcode-allow-loss '!tool_result_multimodal_content'` still reject it).
- Local REQUEST-conversion failures on transcoded routes are now operator-visible: the early-return paths that previously failed a client request silently (decode/render, request body read and size, content-encoding, upgrade, committed-stream mismatch, converter construction) each log one `transcode: <METHOD> <PATH>: [local_request_conversion_error] …` line to the operator stream, with dynamic details bounded and no headers/credentials/URLs; a client-fault query/credential rejection inside request construction logs with the marker (bounded), the internal construction branch keeps its own neutral `build upstream request` line, and signing failures log under their own marker. Response-side stream failures keep their existing outcome/metrics classification and now also log one bounded `[local_response_conversion_error]` line, so a stream that fails mid-conversion is visible to the operator without the journal's classification changing. Signing failures log under their own marker.
- Mid-stream failure after content already streamed when a gateway redelivers the terminal chunk with the usage accounting attached (observed live on Dialagram `meta-muse-spark-1.3`: the finish chunk carries `finish_reason: "tool_calls"` with a role-only delta, `content: ""` and `reasoning: null`, and is then repeated on the same single choice with a role-only delta and `content: ""` plus the `usage` object) instead of sending the bare `choices: []` usage-only tail that `stream_options.include_usage` defines. The redelivery is pure accounting: the converter now folds its usage into the terminal envelope, applies the same loss decisions, and emits no events, so the stream completes to exactly one `message_stop` instead of a `chat stream chunk after finish_reason` error after the thinking/tool blocks had already yielded (Claude Code: "Server error mid-response"). Substantive post-finish payloads — content, reasoning, refusal, tool-call fragments, a non-empty legacy `function_call` payload, a different `finish_reason`, or more than one choice — remain corrupt upstream wire and are rejected; the benign empty-string `function_call` fragment stays absorbed exactly as it is mid-stream. Both shapes are documented in the wire shadow's modeled-extension comments.
- Early committed SSE streams locked against raw JSON contamination and false breaker success: when `-queue-comments` commits `200 OK` and SSE headers before admission, an upstream non-200 status (such as 429 or 5xx) or transcode failure no longer writes raw JSON into the text/event-stream representation or records as an upstream breaker success. Instead, the native transparent path emits a dialect-agnostic `: queue-wait failed: upstream` stream comment and closes the stream while evaluating the upstream status override for breaker accounting and journal capture; the transcoding path renders dialect-legal SSE error events across all upstream HTTP, body, and semantic error writers.
- Transcoded route circuit breaker rejection alignment: when an in-flight request on a transcoded route is rejected because a circuit breaker opened (e.g. during retries), the transcoder emits a native 503 `circuit_open` client-dialect error (or committed-stream error event) and increments `shaper_circuit_rejected_total` as a local rejection without penalizing the circuit breaker as an upstream failure.
- Streaming representation lock with explicit non-streaming request intent: requests carrying an explicit `"stream": false` payload with an `Accept: text/event-stream` header no longer trigger early SSE queue comments, preventing dialect-incompatible commitments. If an already-committed stream encounters `stream: false`, it cleanly terminates with a client-dialect SSE error event rather than raw JSON.
- LIVE 400 with Claude Code (2.1.260) under `-transcode-messages-chat`: `transcode field messages[].tool_result.is_error uses unsupported feature "tool_result_error_status"`. Claude Code marks every failed tool call with `is_error: true`, and the default loss profile did not approve that key, so the request failed before reaching the upstream. The default profile now approves `tool_result_error_status`: the failed tool result renders with the visible `[tool_result_error]` prefix (the model still sees the tool failed) and the decision is logged per exchange. The strict programmatic policy, `-transcode-strict-defaults`, and `-transcode-allow-loss '!tool_result_error_status'` still reject it.
- Documented (no behavior change): what a client sees while a limited request waits in the bounded queue (zero response bytes until admission; size `-queue-timeout` against the client's effective deadline, because agents like Claude Code abort-and-retry past it), the count_tokens limiter-class workaround that stops `POST /v1/messages/count_tokens` from queueing behind streaming completions under `-limit-all`, why `count_tokens` is deliberately never transcoded or estimated against a chat-only upstream, and why provider reasoning renders as ordinary text rather than a synthesized `thinking` block (Anthropic signature semantics make unsigned thinking blocks 400 on replay).
- Metrics/journal ordering: the clean-completion counters (`Clean proxied`, `Clean passthrough`) and their status buckets published before the journal entry, so a consumer polling the snapshot could observe the counter without the matching request log entry — the same window fixed for the aborted pair earlier. The journal entry now publishes first, and the clean counters publish inside finalization gated on actual admission-path completion (queue timeouts, cancellations, and circuit rejections were and remain excluded).
- Three breaker/consistency fixes from an adversarial review: a breaker that opened between retries now produces the same 503 `circuit open` + rejection counter as the pre-flight check (previously a proxy 502 with a blind counter); `proxy.New` validates the programmatic auth policy at construction instead of degrading per request to strip-only forwarding; and a transcode mapping's secret source is resolved once at handler construction, so a mutable source can no longer change live behavior or fail mid-exchange.
- `-transcode-auth bearer` (or any secret-requiring mode) without `-transcode-auth-source` failed startup validation only implicitly: the resolver silently set `inbound` and forwarded the CLIENT credential to the transcode target, contradicting the documented fail-closed default. The missing source is now a startup configuration error (`auth mode requires a secret source or inbound credentials`); `-transcode-auth-source inbound` remains the explicit opt-in, and the README documents the full resolution table.
- Source-inconsistent usage (a cached breakdown exceeding the input total, negative counts, a total that is not input + output) is no longer a failure at all: it is a subject-to-change provider value, so the counts are clamped into the client dialect's invariants (nonnegative, cached components no larger than the input total) and every correction is recorded as an ungated note naming the source numbers (`usage_cache_exceeds_input`, `usage_negative_counts`, `usage_total_mismatch`) — a live `POST /v1/messages` through `-transcode-messages-chat` from a gateway whose cached breakdown exceeded the prompt total previously 502'd after the upstream round-trip, and now completes with a client-dialect-valid response.
- A streamed generation accumulating to the per-part bound (1 MiB) deterministically failed its `[DONE]` terminal release: the generated-frame bound equaled the accumulated bound, so the terminal envelope (which repeats the full content) exceeded it, erroring a COMPLETED upstream conversation and penalizing the circuit breaker. The generated-frame, terminal-batch, and exchange generated-total bounds are now jointly derived from the exchange accumulated-total and the request echo, and the derivation is closed on every axis: worst-case 6x JSON escaping of the accumulated semantics, the 6x-escaped request echo (bounded at decode as a fail-closed 413 resource limit — an unbounded echo previously failed the first upstream frame at ~9.3 MiB of escaping-heavy instructions), per-event framing overhead times the event budget (a legal stream of single-byte deltas previously died at ~69% of the event budget), and tool-call identity charged against the exchange total. Every accepted stream exchange can now complete its release; the amplification protection stays enforced at the new bounds.
- Transcode upstream transport failures no longer echo the raw transport error into the client-facing 502 body: a custom `http.Client`-based transport produces `*url.Error` values carrying the full outbound request URL (including a credential-bearing upstream base query), which could reach the unauthenticated client. The client now receives a neutral dialect error; the detail is logged server-side with sensitive URL query values redacted, recursing through nested error chains like the native passthrough sanitizer.
- A multi-part all-text tool result rendered to a Chat tool message was silently joined into one `\n`-separated string with no observability. The join is now a recorded, sanctioned encoding: every content byte is preserved, the join is logged on every exchange, and it is never policy-rejected (default-rejecting it was a live availability failure with clients that send multi-part tool results).
- Root-package tests no longer compile against nonexistent symbols: the idle-connection test calls the exported `proxy.MaxIdleConnsPerHost`, and `TestValidateMBFlag` lives where its unexported subject does (`internal/config`).
- Live 502 under `-transcode-messages-chat`/`-transcode-responses-chat`: the strict wire decoder now accepts the Verboo gateway's `cache_cost` extension (both placements) as opaque raw JSON and never forwards it.
- Recurring upstream-response 502s on unknown provider-extension fields (`completion_cost`, and the broader provider set): the upstream response decode is now TOLERANT to unknown fields on the subject-to-change provider envelope (a `wire.DecodeTolerant` path), so a field like `completion_cost` never fails a request. The CLIENT request decode and the content-block unions stay STRICT, preserving the lossless-transcoding invariant. `completion_cost` is modeled as opaque raw JSON at both placements and never forwarded.
- Approved-loss logging no longer floods the TUI/log: all approved losses of one conversion are aggregated into a single per-request line, and a per-route loss-profile summary is logged once at startup.
- Native passthrough with an upstream base URL that carries a path query or a trailing slash: the Rewrite hook now uses `pr.SetURL`, merging the base query before the client query and joining paths at the slash boundary (no doubled slashes, no path canonicalization).
- Transcode route keys are canonicalized the same way the router normalizes inbound paths, so a mapping configured as `/v1/responses/` (or with dot segments) dispatches instead of silently falling through to passthrough; canonically-equivalent routes are rejected as duplicates.
- Proxy configuration is frozen at construction: `auth.FreezeAuthPolicy` resolves the credential once (mutable `SecretSource`s can no longer change live behavior), and the route-limiters map and matcher (including `Pattern.Segments`) are copied, so caller mutation after `New` cannot alter routing or auth.
- Transcode auth defaults are documented as implemented — unset inherits the provider auth policy, else strip-only `none`; `-transcode-auth-source provider` is the explicit inheritance opt-in (never `auto`/`inbound` by default).
- A `-h`/`--help` lexeme consumed as the value of a preceding value-taking flag (e.g. `-upstream -h`) is no longer treated as a help request — it fails semantic validation like any other bad value.
- A proxy bind failure no longer leaves a metrics listener running (proxy binds first), and a fatal server error now calls `stop()` and gracefully shuts down every server while preserving the original error.
- Metrics `RecordAbortedRequest` publishes the journal entry before the aborted counter, so a consumer that observes the counter can read the matching log entry.
- `make lint` passes: dead increments in the TUI detail overlay are removed, and the pre-existing deadcode findings are catalogued as confirmed false positives / test-only-exercised wire API in `.deadcodeignore`.
- Upstream gateways emitting the deprecated chat `function_call` spelling (observed on glm-5.3-flash through `-transcode-messages-chat` and `-transcode-responses-chat`): the single invocation now maps to one canonical tool call with the id synthesized from the response id and recorded as the ungated `legacy_function_call` note, on both the streaming delta and the non-streaming message surfaces. A bare `function_call: null` is treated as absent on both. On the STREAMING delta surface, a fragment whose `name` and `arguments` are both present and empty is a benign no-op equivalent to null, a fragment with a name and no `arguments` member completes with `{}` arguments, and `{}` or any null member remains corrupt wire; on the NON-STREAMING message surface the arm requires a present, non-empty `name` and a present `arguments` member, so an empty-string fragment is rejected there. Finally, the optional usage-only tail chunk may omit its envelope identity (id/model/created) while a content-bearing chunk missing any of them still rejects.
- Queue and observability follow-ups: the unlimited admission class bypasses the global limiter; passthrough queue timeouts return `504` with a timeout increment like the limited path; the queued gauge stays held across the global wait so the aggregate never reads `0` with a per-route waiter present; the counter-journal ordering is pinned at the production 51-entry capacity; the outer panic recovery respects an already-written terminal; the metrics endpoint test uses bounded clients; the SSE readiness poll replaces fixed sleeps; and the queue-depth tests close their gates on every path.

- Documented (no behaviour change): the README transcode defaults table now lists `structured_outputs` alongside `parallel_tool_calls` and `provider_reasoning_thinking` (the code enables the capability by default), the model table's wire charset is stated in full, and the served catalog's accepted aliases and query parameters are enumerated.

### Changed
- `image_input` and `stop_sequences` are default chat capabilities: Claude Code attaches images as a matter of course, and stop sequences are a standard Messages request field — rejecting either locally turned a real request into a local 400 before the upstream was asked. Withdraw either with `-transcode-chat-capability '!image_input'` / `-transcode-chat-capability '!stop_sequences'` for an upstream that genuinely cannot accept the corresponding chat fields.
- The default loss approvals now cover the response controls a native Responses upstream echoes on its responses: `response_service_tier` and `output_phase` (the tier actually served and the output message phase cannot be reproduced in a client dialect, so they are dropped observably instead of failing the exchange). Observed live: a gateway serving the native Responses API emitted both on the captured response, so `-transcode-messages-responses` failed at response conversion before reaching the client.
- Default reasoning rendering flipped to native thinking (`provider_reasoning_thinking` is now a default chat capability; `provider_reasoning_text` is off by default): Claude Code receives provider reasoning as native Anthropic thinking blocks out of the box and renders it with its native thinking UI — live-verified against Claude Code 2.1.260 (thinking lifecycle streams correctly and replayed synthetic blocks are scrubbed before the upstream sees them). The stream also now seals the thinking block at the reasoning→content transition (signature_delta + content_block_stop before the text block opens) instead of holding every item close until the [DONE] sentinel, which previously emitted two concurrently-open blocks and an out-of-order signature. Restore the old ordinary-text rendering with `-transcode-chat-capability '!provider_reasoning_thinking' -transcode-chat-capability provider_reasoning_text`.
- `-transcode-auth-source` accepts `provider` (explicit provider-auth inheritance; conflicts with `-transcode-auth`/`-transcode-auth-header`, requires a configured provider auth source).
- The metrics endpoint binds after the proxy listener; a bad `-metrics-bind` address fails at startup with the proxy listener already released.
- The provider-scope `-transcode-model` flag is retired whenever the global table exists: a configuration carrying both `-model-table` and any provider's `-transcode-model` fails startup naming the provider (`configure the global table only`), because one scope must own model identity. A legacy configuration using `-transcode-model` alone behaves exactly as before, and migration moves each `client=upstream` entry to `-model-table` as `client@provider=upstream` (worked examples in the README).
